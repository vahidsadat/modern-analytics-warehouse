# Modern Analytics Warehouse with dbt and PostgreSQL

## Project Overview

This project is a modern analytics warehouse built with **Python**, **PostgreSQL**, and **dbt**.

The goal of the project is to transform raw e-commerce data into clean, reliable, and business-ready analytics models. The final models can be used for reporting, dashboarding, and business analysis.

The project follows a typical analytics engineering workflow:

```text
raw data → staging models → intermediate models → dimensions/facts → business marts
```

## Business Context

The project simulates a fictional e-commerce company that wants to better understand its sales, customers, products, payments, web traffic, and marketing performance.

The main business questions are:

- How much revenue does the company generate each day?
- Who are the most valuable customers?
- Which products perform best?
- Which marketing channels generate the best return?
- How do order statuses, payments, and returns affect business performance?

## dbt Layer Design

The dbt project is divided into three main transformation layers.

### 1. Staging Layer

The staging layer cleans and standardizes the raw source tables.

Staging models have a one-to-one relationship with the raw tables. They are used to rename columns, cast data types, create basic calculated fields, and prepare the data for further transformation.

Example staging models:

- stg_customers
- stg_products
- stg_orders
- stg_order_items
- stg_payments
- stg_web_sessions
- stg_marketing_spend

The staging layer does not contain complex business logic. Its main goal is to make raw data clean and consistent.

### 2. Intermediate Layer

The intermediate layer applies business logic and joins multiple staging models together.

This layer helps avoid large and complicated SQL queries in the final marts. Each intermediate model has a clear purpose and prepares reusable business logic.

Example intermediate models:

- int_order_items_enriched
- int_orders_enriched
- int_customer_order_history
- int_daily_channel_revenue

Examples of logic in this layer:

- joining orders with order items
- joining order items with products
- calculating total cost
- calculating gross margin
- creating order status flags
- calculating customer order history

### 3. Marts Layer

The marts layer contains the final analytics-ready models.

These models are designed for business users, dashboards, and reporting. The marts layer contains dimensions, facts, and business summary tables.

Dimensions:

- dim_customers
- dim_products
- dim_dates

Facts:

- fact_orders
- fact_order_items
- fact_payments
- fact_web_sessions
- fact_marketing_spend

Business marts:

- mart_daily_sales
- mart_customer_lifetime_value
- mart_product_performance
- mart_marketing_roi

## Final Business Marts

### mart_daily_sales

This mart provides daily sales performance.

Grain:

```text
one row per order date
```

Main metrics:

- total orders
- completed orders
- cancelled orders
- returned orders
- gross revenue
- net revenue
- paid revenue
- total cost
- gross margin
- average order value
- refund rate
- cancellation rate

### mart_customer_lifetime_value

This mart analyzes customers and their lifetime value.

Grain:

```text
one row per customer
```

Main metrics:

- total orders
- completed orders
- lifetime net revenue
- lifetime paid revenue
- lifetime gross margin
- average order value
- customer segment

Customer segments:

- No Purchase
- Low Value
- Regular
- High Value
- VIP

### mart_product_performance

This mart analyzes product-level performance.

Grain:

```text
one row per product
```

Main metrics:

- total quantity sold
- total orders
- gross revenue
- net revenue
- total cost
- gross margin
- gross margin percentage
- return count
- return rate

### mart_marketing_roi

This mart compares marketing spend with revenue generated by customer acquisition channels.

Grain:

```text
one row per spend date and marketing channel
```

Main metrics:

- spend
- impressions
- clicks
- completed orders
- net revenue
- paid revenue
- gross margin
- cost per click
- conversion rate
- ROAS
- marketing ROI

## Data Modeling Approach

This project uses a dimensional modeling approach.

Fact tables contain business events and measurable values, such as orders, order items, payments, web sessions, and marketing spend.

Dimension tables contain descriptive information, such as customer details, product information, and calendar dates.

Business marts aggregate facts and dimensions into final reporting tables.

## Testing

dbt tests are used to check data quality and model reliability.

The project includes tests for:

- primary keys
- not-null columns
- unique values
- relationships between facts and dimensions
- accepted values for statuses and channels
- final mart grain validation

Examples:

- customer_id should be unique in dim_customers
- product_id should be unique in dim_products
- order_id should be unique in fact_orders
- order_status should only contain completed, cancelled, or returned
- sales_channel should only contain web, mobile_app, or marketplace

## How to Run the Project

### 1. Create and activate a virtual environment

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 2. Install dependencies

```bash
pip install dbt-core dbt-postgres
```

### 3. Configure dbt profile

Create or update the dbt profile file:

```text
~/.dbt/profiles.yml
```

Example profile:

```yaml
dbt_project:
  target: dev
  outputs:
    dev:
      type: postgres
      host: 127.0.0.1
      user: your_postgres_user
      password: your_postgres_password
      port: 5432
      dbname: warehouse
      schema: analytics
      threads: 4
```

### 4. Check dbt connection

```bash
dbt debug
```

### 5. Run dbt models

```bash
dbt run
```

### 6. Run dbt tests

```bash
dbt test
```

### 7. Build models and tests together

```bash
dbt build
```
